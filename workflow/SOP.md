# 轻量研发 SOP

## 1. 适用方式

本 SOP 规定任务必须达到的最低状态，不规定个人必须采用相同的分析过程。角色可由产品、设计、开发、测试或同一人兼任。

## 2. 第一步：任务分级

任务进入后按 [TASK-LEVELS](TASK-LEVELS.md) 判断等级。满足任一高等级条件时采用较高等级；拿不准时先按 L2，只有发现真实风险后再升级。

分级决定最低文档，不决定开发周期和人员数量。

三种使用方式：

| 等级 | 最低产物 | 适用方式 |
| --- | --- | --- |
| L1 | TASK + 验证结果 | 小改动和明确缺陷 |
| L2 | 一份 SPEC + 验证结果 | 大多数普通功能 |
| L3 | PRD + SDD + TEST-PLAN + DELIVERY，ADR 按需 | 完整正规流程 |

L3 从 [正式功能模板包](templates/FORMAL-FEATURE/README.md) 开始。模板提供完整覆盖，章节按 `[必填]`、`[条件必填]`、`[可选]` 使用；模板完整不等于所有内容都必须填写。

## 3. Ready：可以开始做

所有任务开始实现前，至少确认：

- [ ] 问题、目标或预期变化已经说清楚。
- [ ] 本次范围和明确不做的内容没有关键歧义。
- [ ] 验收标准可观察、可验证。
- [ ] 依赖、权限、数据或外部协调不存在未知阻塞。
- [ ] 任务等级和最低产物已经确定。
- [ ] 已知道本任务哪些产物分别负责需求、设计、契约和验证；L1 无需额外制作权威清单。

Ready 不要求所有细节提前冻结。实现中可以补充细节，但影响目标、范围或验收的变化必须回到任务文档确认。

正式 L3 项目以 PRD 作为 Ready 的主要产物；PRD 未明确目标、非目标、关键规则和可验证 AC 时，Ready 为 Fail。

## 4. Build：必要设计已经确认

仅当任务包含下列情况时设置开发前设计确认：

- 公共接口、协议、数据结构或持久化变化。
- 跨系统、跨团队或多个核心模块协作。
- 数据迁移、兼容、权限、安全、资金或隐私风险。
- 难以回滚、长期维护成本高或有明显技术选型分歧。

确认内容只需覆盖相关部分：总体方案、关键数据与接口、失败处理、兼容回滚、主要替代方案。普通 L1/L2 任务不设置独立 Build 审批。

正式 L3 项目以 SDD 和 TEST-PLAN 作为 Build 的主要产物：SDD 说明如何实现及如何失败和恢复，TEST-PLAN 说明如何证明正确。TDD 是开发方法；Red/Green/Refactor 证据由测试代码和结果承担，不要求重复建立 TDD 报告。

## 5. 开发验证 Loop

每次选择一个可独立验证的最小行为：

1. 将行为对应到验收项或测试列表。
2. 可以自动化且风险合适时，先写会因缺少实现而失败的测试（Red）。
3. 编写使测试通过的最小实现（Green）。
4. 在测试保护下重构代码和测试（Refactor）。
5. 运行相关回归测试并记录必要证据。
6. 继续下一个行为。

核心业务规则、缺陷修复、数据转换和稳定接口优先测试先行。纯视觉调整、探索性原型或难以稳定自动化的场景可不执行严格测试先行，但必须说明验证方式。

## 6. 变更处理

- 不影响目标、范围和验收的实现细节：直接更新 SPEC/SDD 后继续。
- 改变用户行为、范围或验收：回到 Ready，由相关人员确认。
- 改变公共接口、数据或关键技术选择：回到 Build，并更新 SDD/ADR。
- 发现任务等级过低：升级等级并补齐从当前时点起真正需要的内容，不倒填无价值材料。

## 7. 评审与提交

- 文档与代码关联同一个任务、分支和 PR/MR。
- 文档可以在代码前先行评审，也可以随代码一起评审，不建立第二套提交系统。
- 评审关注目标是否正确、设计风险是否受控、测试是否证明行为，而非模板是否填满。
- L3 任务建议在大规模实现前完成需求和关键设计确认。
- 实现结束后，必要文档必须反映最终行为；历史讨论留在任务或 ADR，不塞回正文。
- L3 的实施结果、测试执行、偏移、遗留和最终结论统一进入 DELIVERY；不要再创建内容重复的实施报告、测试报告和状态报告。

## 8. Align：文档与交付对齐

Align 是所有任务进入 Done 前的必经 Gate，但不是新的审批系统，也不能替代开发过程中的即时更新。作者在现有任务或 PR/MR 中执行，评审者按任务等级检查；若最后才集中补写大量文档，说明前面的变更处理没有执行好。

### 8.1 分层权威

| 信息类型 | 权威来源 |
| --- | --- |
| 目标、范围、业务规则、验收标准 | TASK/SPEC/PRD |
| 关键设计、边界、失败语义、兼容策略 | SPEC/SDD |
| 重大选择和理由 | ADR |
| 公共接口、Schema、迁移、配置约束 | 可执行接口定义、Schema、迁移和配置校验 |
| 测试覆盖与执行结果 | 测试代码、流水线和验证证据 |
| 当前实现与线上状态 | 代码、配置、指标、日志和运行证据 |

文档对意图和设计具有规范性权威；代码和运行证据反映实际状态。两者冲突时必须分类并解决，不能默认任何一方永远正确。

### 8.2 检查内容

- [ ] 最终用户行为没有遗漏或超出确认的范围与 AC。
- [ ] 实际架构、失败语义、兼容和回滚符合 SPEC/SDD/ADR。
- [ ] 公共接口、数据、配置与可执行定义一致，文档不重复维护易漂移的机械细节。
- [ ] 每条阻断级 AC 都有测试或人工验证结果。
- [ ] 实现中产生的新决定已经进入对应权威来源。
- [ ] 文档变更与代码在同一任务和 PR/MR 中提交。

### 8.3 偏移处理

| 偏移 | 处理 |
| --- | --- |
| 实现不满足已确认意图 | 修正代码和测试，重新 Align |
| 已批准实现变化但文档仍是旧内容 | 更新对应文档，重新 Align |
| 用户行为、范围或 AC 改变 | 回到 Ready，更新 TASK/SPEC/PRD |
| 公共契约、数据或关键方案改变 | 回到 Build，更新 SDD/ADR |
| AC 缺少验证 | 补测试或验证；不能用待办绕过阻断项 |

权威内容仍有冲突时 Align 为 `Fail`，不得进入 Done。L1/L2 默认把结果记录在交付检查中；L3 默认记录在 [DELIVERY](templates/DELIVERY.md)；只有独立审计要求才额外使用 [ALIGNMENT-GATE](templates/ALIGNMENT-GATE.md)。

## 9. Done：真正完成

任务关闭前至少满足：

- [ ] 验收标准逐项通过或明确记录例外。
- [ ] 必要自动化测试、构建和静态检查通过。
- [ ] 人工验证有简短结果；高风险任务保留可定位证据。
- [ ] Align Gate 为 Pass，不存在未解决的权威冲突。
- [ ] 临时代码、调试入口、无效注释和废弃分支已清理。
- [ ] 公共接口、配置、迁移、运维或用户文档已按需同步。
- [ ] 未完成项、已知风险和后续任务已明确记录。
- [ ] PR/MR 可说明改了什么、为什么安全、如何验证。

L1/L2 直接使用 [DELIVERY-CHECKLIST](templates/DELIVERY-CHECKLIST.md) 完成检查；L3 使用 [DELIVERY](templates/DELIVERY.md) 汇总实际结果并完成 Align。

## 10. 流程例外

紧急故障可以先恢复服务，但任务中必须记录原因、临时措施和验证结果；涉及临时绕过或技术债时补建后续任务。例外不是补写全部模板的理由。

## 11. SOP 自身的优化规则

本 SOP 是试运行中的工作基线，不是不可修改的制度。任何参与者都可以在实际使用中提出优化；提出问题本身不视为违反流程。

只有满足以下任一条件时才增加强制项：

- 已发生的缺陷或事故可被该检查直接预防。
- 多次交接都因同一信息缺失而失败。
- 法规、安全、审计或发布制度明确要求。

若某项长期无人使用、无法参与决策或无法验证，应删除、合并或改为条件项。

优化建议至少说明使用场景、当前问题、实际影响和建议变化。能够附带返工、缺陷、评审耗时、交接困难或重复维护案例时优先处理。单纯为了“看起来更完整”或只基于个人写作偏好的建议，不增加为公司强制项。

流程维护者应定期把建议处理为以下结论之一：

- 接受：更新 SOP/模板、版本号和受影响示例。
- 试验：限定团队或任务类型试运行，明确观察指标。
- 拒绝：记录理由，避免相同讨论反复发生。
- 暂缓：说明缺少的证据或触发重新评估的条件。

任何流程修改都应重新执行 Align Gate，确认 README、SOP、模板和示例保持一致。
