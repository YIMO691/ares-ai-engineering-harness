# AI 研发工作流执行协议

## 1. 目标

帮助新人和开发团队把原始需求转化为最小充分文档、可执行拆解、经过验证的实现和可追踪的交付结果。AI 是工程执行与分析助手，不是产品意图、风险接受或证据真实性的最终决定者。

## 2. 上下文读取顺序

不要一次性加载所有模板。

1. 读取项目自身的 `UPSTREAM-AGENTS.md`、安全边界、构建说明和现有工程规范。
2. 读取本工作流的 `README.md`、`TASK-LEVELS.md` 与当前 Gate 对应的 `SOP.md` 章节。
3. 检查代码、配置、接口、测试和已有需求/设计文档，先获得工程事实。
4. 判断 L1/L2/L3 后，只读取该等级需要的模板和最接近的示例。
5. L3 读取正式功能模板包；需要重大技术决定时才读取 ADR，只有独立审计要求才读取 ALIGNMENT-GATE。

## 3. 首次任务处理

### 3.1 先区分请求类型

- 解释、评审、诊断：只读检查并给出结论，不擅自实现。
- 规划或设计：检查工程后产出决策完整的方案，不修改生产代码。
- 修改或实现：完成 Ready；存在高风险设计时完成 Build，然后实现、验证、Align 和清理。
- 仅提供原始需求但授权不清：先完成只读分析和 Ready 输出，再说明下一步需要的授权。

### 3.2 先探索，再提问

工程可以回答的问题必须先检查，不向新人询问文件位置、已有类型或现行行为。只询问无法从工程发现且会实质改变目标、范围、风险或方案的决策。

### 3.3 任务分级

给出等级、证据和最低产物：

- L1：TASK 或任务/PR 描述。
- L2：单份 SPEC。
- L3：使用正式功能模板包，PRD、SDD、TEST-PLAN 和 DELIVERY 构成完整流程；ADR 和独立 ALIGN 仍是条件产物。

不得因为内容复杂、AI 能生成文档或模板存在，就自动升级等级或创建全部文件。

## 4. AI 固定输出契约

### 4.1 Intake / Ready 输出

```text
当前 Gate：Ready / Pass 或 Fail
任务理解：
工程现状与证据：
任务等级与理由：
最低必要产物：
范围与非目标：
验收标准：
功能点拆解：
关键风险：
待用户决定的问题：
下一步：
```

功能点拆解至少包含：

| 功能点 | 用户/系统行为 | 输入与输出 | 依赖与约束 | 对应 AC | 验证方式 |
| --- | --- | --- | --- | --- | --- |

只有真实存在的内容才进入表格，不为了填满列而发明接口或风险。

### 4.2 Build 输出

```text
当前 Gate：Build / Pass 或 Fail
方案摘要：
关键数据、接口与流程：
失败、兼容和回滚：
已确认决策与 ADR：
实现增量及每步验证：
未解决的阻断项：
```

实现增量必须能单独验证；不要只给逐文件修改清单，也不要把尚未确认的产品选择交给实现者自行决定。

### 4.3 执行更新

长任务每个重要增量后简要报告：已完成行为、改变的权威产物、测试结果、发现的偏移、下一增量。不要用篇幅代替证据。

### 4.4 Align / Done 输出

```text
当前 Gate：Align / Pass 或 Fail
需求与最终行为：
设计与公共契约：
AC 与测试/证据：
发现并修正的偏移：
未解决冲突：
清理与遗留：
Done 结论：
```

L3 应把上述结果写入 DELIVERY，且只在 DELIVERY 汇总实际实施状态、测试结果、偏移和最终交付决定。不要再生成内容重复的实施报告、测试执行报告或状态报告。

## 5. Gate 行为

### Ready

- 目标、范围、非目标和 AC 可理解、可验证。
- 工程事实与用户意图分开记录。
- 关键产品决策缺失时 Fail，不自行猜测。

### Build

- 仅高风险、公共契约、迁移、跨系统或难回滚任务需要正式通过。
- 设计必须覆盖真正存在的失败和兼容风险。
- 重大选择保留理由与替代方案。

### 开发验证 Loop

- 将功能点拆成可独立验证的最小行为。
- 核心规则和缺陷修复优先 Red → Green → Refactor。
- 不适合测试先行时记录替代验证，不伪造 Red 或测试结果。
- 每个增量通过后再进入下一个，持续更新发生变化的权威文档。

### Align

- 按 SOP 的分层权威比较需求、设计、可执行契约、代码、测试和运行证据。
- 需求变化回 Ready；设计或契约变化回 Build；实现错误修代码；文档过期更新文档；验证缺口补证据。
- 没有访问代码、测试或运行证据时必须明确限制，不能宣布 Align Pass。

### Done

- 只有 Align Pass、验证完成、必要清理和遗留记录完成后才能 Done。
- “文档已经写完”“代码能够编译”或“AI 认为合理”都不能单独证明 Done。

## 6. 文档更新规则

- PRD/SPEC 管需求意图，不塞入易变化的代码细节。
- SDD 管关键设计与约束，公共接口机械字段链接可执行定义。
- ADR 只记录重大、长期或难逆决定。
- TEST-PLAN 记录测试策略与映射，实际结果必须引用真实证据。
- DELIVERY 是 L3 的实施结果、测试结果、偏移、Align 和交付决定的唯一汇总；只引用原始证据，不复制完整日志。
- 文档和代码在同一任务与 PR/MR 中更新。
- 已有任务系统维护的状态、负责人等元数据不重复双写。

## 7. 停止与升级条件

遇到以下情况应停止当前路线并报告：

- 缺少会改变目标、范围或风险接受的用户决定。
- 操作超出授权、写入边界或可能造成不可恢复影响。
- 现有实现与权威需求发生冲突且无法判断哪一方已获批准。
- 必须测试或证据无法获得，仍会影响交付结论。
- 连续尝试无法通过同一关键验证。

报告必须包含已确认事实、阻断原因、已经尝试的检查和最小所需决定。

## 8. 流程优化反馈

使用中若发现模板重复、Gate 无价值、AI 容易误解或现有流程漏掉真实风险，在最终交付中增加简短“流程反馈”：场景、问题、实际影响、建议和证据。不要未经授权直接把个人偏好升级为公司强制规则。
