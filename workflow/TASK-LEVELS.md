# 任务分级规则

## 1. 分级原则

等级用于控制文档成本。它基于风险和协作复杂度，不单纯依据代码行数或排期天数。

## 2. 判断表

| 维度 | L1 小改动 | L2 标准功能 | L3 复杂或高风险项目 |
| --- | --- | --- | --- |
| 用户影响 | 局部修复，行为明确 | 新增或调整完整用户行为 | 多角色、多流程或重要业务闭环 |
| 技术范围 | 单点、低耦合 | 一个或少数模块 | 跨系统、跨团队或多个核心模块 |
| 接口与数据 | 不改公共契约 | 局部可兼容变化 | 新公共接口、持久化、迁移或协议变化 |
| 风险 | 易验证、易回滚 | 中等风险 | 安全、资金、隐私、数据损坏、难回滚 |
| 决策 | 基本无方案分歧 | 有少量设计选择 | 有重大选型、替代方案或长期影响 |
| 测试 | 单元或人工验证即可 | 需要多层测试 | 需要专项、故障、性能或发布验证 |

只要命中一个明显的 L3 条件，就按 L3 管理相关部分；不要求把所有 L3 章节写满。

## 3. 最低产物

### L1 小改动

- 一份 `TASK`，可以直接放在 Issue、任务卡或 PR/MR 描述中。
- 完成验收和交付检查；Align 只确认 TASK、实现和验证一致。
- 不要求单独 PRD、SDD 或测试方案。

### L2 标准功能

- 一份 `SPEC.md`，集中记录需求、设计、测试和交付信息。
- 关键决定可直接写在 SPEC；只有长期或重大决定才另建 ADR。
- Align 逐项检查 SPEC 的 AC、关键设计和验证结果，结论放在交付清单。
- 不要求把 SPEC 拆成多份文档。

### L3 复杂或高风险项目

- 从 [正式功能模板包](templates/FORMAL-FEATURE/README.md) 开始，使用完整正规流程。
- `PRD.md`：需求意图与验收基线。
- `SDD.md`：关键设计、失败处理和兼容回滚。
- `TEST-PLAN.md`：跨层验证、专项测试和发布条件。
- `DELIVERY.md`：最终实现、测试结果、偏移、Align 和交付决定的唯一汇总。
- `ADR`：仅用于重大且难逆的决策。
- Align 对齐 PRD、SDD、ADR、可执行契约和测试证据；默认记录在 DELIVERY，仅独立审计场景另建 ALIGNMENT-GATE。
- 客户端、服务端或子系统文档只有在单份 SDD 已影响阅读和评审时才拆分。

## 4. 快速判断

```text
是否涉及重大业务风险、公共契约、数据迁移、跨系统或难回滚？
├─ 是 → L3
└─ 否
   └─ 是否形成新的完整行为，或需要解释设计与多层验证？
      ├─ 是 → L2
      └─ 否 → L1
```

## 5. 升降级

- 实现中出现新风险可以随时升级。
- 需求收缩后可以降级，但已经产生且仍有维护价值的设计决定应保留。
- 不允许为了规避评审故意拆成多个 L1。
- 不允许仅因模板已经创建就维持不必要的高等级。
