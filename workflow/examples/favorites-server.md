# 收藏功能：服务端实现示例

[功能入口与 AC](L2-standard-feature.md) · [客户端实现](favorites-client.md) · [验证与验收](favorites-verification.md)。对应教学基线 A，所有实现均为拟议，尚无服务、数据库、代码路径或执行环境。

## 业务与数据

AC-01 拟定链路：`SetFavoriteHandler` → 当前会话身份 → 参数及权限校验 → `FavoriteService.SetState` → 收藏记录和操作结果写入 → 返回确认。数据归属按账户，收藏记录拟以 `(accountId, itemId)` 唯一约束；重试使用设置期望状态，不使用 toggle。

期望已收藏时插入或确认已存在；期望未收藏时删除或确认已不存在。仅先查询再插入会有竞争，实际保证要落到项目存储支持的事务/唯一约束和错误处理，不能以应用层先查一次代替。对同一条目的并发相反意图，还需要已约定顺序或版本冲突处理；唯一约束仅防重复记录。

## 权限与查询

AC-02：账户来自当前身份，不接受客户端指定另一个账户；添加和重复添加检查当前内容权限。取消本人已有收藏可在内容撤权后执行，规则依据见 [功能需求](L2-standard-feature.md#需求与边界)。

列表只读本人记录并按当前权限过滤；直接请求、操作结果查询都校验账户归属。不能仅让客户端隐藏按钮。真实实现后应链接鉴权入口与查询过滤位置，并执行 [V-02](favorites-verification.md#v-02-权限与隔离)。

## 操作结果与恢复

AC-03 拟采用既有持久化设施保存操作身份、请求摘要和最终结果；同一身份不同请求必须拒绝复用。本例假设操作结果与收藏数据可在同一事务提交，若实际跨存储则此方案不成立，需重新设计一致性及恢复。

| 故障位置 | 必须核实的行为 |
|---|---|
| 事务提交前失败 | 数据与成功结果都未提交；实际重试仍遵守同一身份和权限规则 |
| 提交成功后响应丢失 | 查询可取得对应最终结果；重试不重复产生业务效果 |
| 请求迟到、查询先到 | “未找到”不能解释为永久失败；不能在此依据下放行相反写入 |
| 同一操作并发到达 | 操作身份的唯一约束/事务保证单个有效结果，并处理冲突后的读取 |
| 结果已清理或账户权限变化 | 返回语义、保留期和恢复方式待决定；不能承诺无限期幂等或绕过鉴权 |

最终操作结果只说明该次写入发生了什么；另一次操作可能随后改变收藏状态，客户端仍需状态版本或重新核实。跨设备冲突和到期恢复未落实，是本示例的验收缺口。

若排查“按钮显示失败但列表里有收藏”，沿操作身份核对提交点、最终数据、响应返回和客户端事件顺序；先区分明确拒绝与响应丢失，再决定修复或恢复。故障注入的验证边界见 [V-03](favorites-verification.md#v-03-响应丢失与迟到)。

## B 的影响

B 尚未实施。拟加限额时，已存在条目的合法重复设置先确认成功；新增条目才进行限额判断。去重、计数和插入须处于同一账户级的并发保护范围，否则两个请求读到 99 都可能插入成功。

可比较存储事务内的账户级串行化，与带条件更新的计数器：前者可能产生锁等待；后者增加计数一致性和修复成本。按项目存储能力选择并实测，不假定单进程锁可覆盖多实例。

上线前仍需确定旧超限账户、撤权条目是否计数、错误码兼容及迁移/回退方式。基线 A 的去重检查不证明 B 的限额正确，须执行 [B 的重验](favorites-verification.md#b-的重验)，并更新实际协议/配置、代码入口及版本。
