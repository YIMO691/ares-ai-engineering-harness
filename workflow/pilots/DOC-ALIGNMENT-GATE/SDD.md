# 1. 设计摘要

在现有评审与 Done 之间增加 Align Gate。Gate 不比较文档篇幅，而是按信息类型检查其权威来源与最终交付是否一致。默认使用交付清单记录结果，不创建新审批系统。

# 2. 当前流程与改动范围

当前流程为 `Ready → 可选 Build → 开发验证 Loop → 评审 → Done`。改为：

```text
Ready → 可选 Build → 开发验证 Loop → 评审 → Align → Done
```

改动 README、SOP、模板和示例；不增加服务、数据库或外部平台依赖。

# 3. 分层权威模型

| 信息类型 | 权威来源 | 不应重复维护的位置 |
| --- | --- | --- |
| 需求目标、范围、业务规则、验收标准 | TASK/SPEC/PRD | SDD 和代码注释不复制完整需求 |
| 关键设计、边界、失败语义、兼容策略 | SPEC/SDD | PRD 不规定实现细节 |
| 重大选择及理由 | ADR | 不依赖会议记忆或聊天记录 |
| 公共接口、Schema、配置约束 | 可执行接口定义、Schema、迁移和配置校验 | SDD 只解释语义并链接来源 |
| 测试覆盖与验证结果 | 测试代码、流水线和验证证据 | TEST-PLAN 不伪造执行结果 |
| 当前实现行为 | 代码和测试 | 文档不能替代实际检查 |
| 线上运行状态 | 指标、日志、告警和事故记录 | 设计文档不作为运行证据 |

“文档权威”因此是有范围的规范性权威：PRD 可以判断实现是否偏离意图，但不能证明线上实际行为；代码可以证明当前实现，却不能自行改变已经确认的产品意图。

# 4. Gate 输入与输出

输入：任务产物、代码/配置变更、测试和验证结果、PR/MR 说明。

输出：

- `Pass`：权威内容与交付一致，可以进入 Done。
- `Fail`：存在未解决的意图、设计、契约或验证冲突，阻止 Done。
- 非权威的说明性材料可登记后续清理，但不得用后续任务绕过核心冲突。

# 5. 对齐算法

1. 根据任务等级确定检查深度和本任务权威来源。
2. 从每条 AC 反查测试或人工验证结果。
3. 检查最终用户行为是否超出或遗漏确认范围。
4. 检查公共接口、数据、配置和失败语义是否符合 SDD/ADR；机械细节以可执行定义为准。
5. 检查实现中出现的新决定是否已进入 SDD/ADR，而不是只留在代码或聊天中。
6. 对差异分类并处理，重新检查直至 Pass。

# 6. 偏移分类与处理

| 偏移类型 | 典型表现 | 处理方式 | 重新确认者 |
| --- | --- | --- | --- |
| 实现错误 | 代码不满足已确认 AC | 修正代码和测试 | 原评审者 |
| 文档过期 | 实现已按批准方案变化，正文仍描述旧方案 | 更新对应权威文档 | 原评审者 |
| 需求变化 | 用户行为或范围发生改变 | 更新 TASK/SPEC/PRD，并回到 Ready | 需求负责人 |
| 设计变化 | 公共契约、数据或关键方案改变 | 更新 SDD/ADR，并回到 Build | 技术负责人 |
| 验证缺口 | AC 没有测试或证据 | 补测试/验证或明确撤销 AC | 开发/测试负责人 |

# 7. 分级执行

- L1：作者在 PR/MR 中确认 TASK、实现和验证一致；评审者抽查。
- L2：逐项对齐 SPEC 的 AC、关键设计和测试表；结果记录在交付清单。
- L3：对齐 PRD、SDD、ADR、可执行契约和 TEST-PLAN；高风险任务可保存独立结果。

# 8. 失败与例外

Align Fail 不能进入 Done。紧急故障恢复可先发布，但必须明确临时状态、权威来源和补齐时限；不得伪记 Pass。
