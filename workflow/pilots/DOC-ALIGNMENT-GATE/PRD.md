# 1. 需求结论

所有研发任务在 Done 前经过一次与任务等级匹配的文档对齐检查。检查用于确认最终交付没有偏离已确认的需求意图、关键设计、公共契约和验收标准；它复用现有任务与 PR/MR，不建立新的审批系统。

# 2. 背景与目标

现有 SOP 只在 Done 中以一个复选项要求“必要文档已同步”，无法回答同步哪些文档、以谁为准、冲突如何处理。结果可能是文档长期过期，也可能出现用旧文档否定已经批准的设计变化。

## 目标

- G-01：任务关闭前能发现并解决有维护价值的信息偏移。
- G-02：为需求意图、设计决策、公共契约和实际行为定义分层权威。
- G-03：检查成本随 L1/L2/L3 分级，不增加独立流转系统。

## 非目标

- NG-01：不要求文档逐行描述代码实现。
- NG-02：不建设完整需求追踪平台或自动理解代码的 AI Gate。
- NG-03：不要求所有任务新增一份对齐报告。
- NG-04：不以文档为理由保留已经被批准变更替代的旧行为。

# 3. 用户与场景

- 作者在提交 PR/MR 前检查最终实现与必要文档。
- 评审者确认差异已经解决，而不是只确认“有文档”。
- 产品或技术负责人只在需求意图、公共契约或重大设计发生变化时参与重新确认。
- 后续维护者能从指定权威来源理解当前意图和关键约束。

# 4. 用户流程与业务规则

1. Ready 时确定任务等级和本任务需要维护的权威来源。
2. 开发中若意图或设计变化，立即更新对应来源，不等到最后补写。
3. PR/MR 进入 Done 前执行 Align Gate。
4. 发现偏移后分类为：实现错误、文档过期、已批准变更未回写、测试或证据不足。
5. 修正对应来源并重新检查；权威内容仍冲突时 Gate 失败。
6. L1/L2 在交付检查中记录结论；只有 L3、高风险或审计场景保留独立对齐结果。

# 5. 功能需求

| ID | 需求 | 优先级 | 说明 |
| --- | --- | --- | --- |
| FR-01 | 定义分层权威模型 | Must | 每类信息只有明确来源 |
| FR-02 | 增加 Align Gate | Must | 位于评审后、Done 前 |
| FR-03 | 提供偏移分类与处理规则 | Must | 决定更新代码、文档或重新确认 |
| FR-04 | 按任务等级裁剪 | Must | L1/L2 不增加独立文档 |
| FR-05 | 提供可复制检查模板 | Must | 并入交付清单，L3 可独立留证 |

# 6. 验收标准

| ID | 对应需求 | 可验证结果 |
| --- | --- | --- |
| AC-01 | FR-02 | README 和 SOP 的主流程包含 Align Gate |
| AC-02 | FR-01 | SOP 能明确回答需求、设计、契约、实现和运行事实分别以什么为准 |
| AC-03 | FR-04 | L1/L2 只增加交付清单中的检查，不强制新建报告 |
| AC-04 | FR-03 | 四类偏移都有明确处理路径和阻断条件 |
| AC-05 | FR-05 | 模板可对 L1、L2、L3 示例完成对齐检查 |

# 7. 依赖、风险与待确认项

- 风险：若把“文档权威”理解为任何文字都高于可执行事实，会掩盖文档过期。
- 风险：若每次都要求独立签字和报告，会重新变成重型流程。
- 决策：采用分层权威和同一 PR/MR 内的 Gate，见 ADR-0001。
