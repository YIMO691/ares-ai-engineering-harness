# 文档对齐 Gate 试运行报告

> 历史说明：本文记录 v0.2 阶段的试运行过程。v0.4 起，L3 默认使用 `DELIVERY.md` 汇总实施、测试和 Align；仅独立审计要求才额外建立 `ALIGNMENT-GATE.md`。当前规则以根目录 README 和 SOP 为准。

## 1. 试运行方式

将“增加文档对齐 Gate”作为 L3 工作流功能，依次完成任务定义、PRD、SDD、TEST-PLAN、ADR、实际模板修改、三级场景演练和最终 Align。

这不是生产代码功能测试，而是对 SOP 和模板的桌面演练与结构验证。

## 2. 产生的问题

### 问题一：原有 Done 检查太模糊

“必要文档已同步”无法判断同步范围、权威来源和冲突处理。它容易被机械勾选。

优化：增加独立 Align Gate，明确输入、检查内容、偏移分类和 Fail 条件。

### 问题二：“文档权威”容易被误解

如果所有文档一律高于代码，过期文档会压过真实实现；如果代码是唯一真相，产品意图和决策理由又会丢失。

优化：采用分层权威。PRD/SPEC 管意图，SDD/ADR 管关键设计，可执行契约、测试、代码和运行证据分别管机械契约、实现与线上事实。

### 问题三：Gate 可能制造第二套审批流

若每个任务都新增对齐报告、签字和流转，L1/L2 会立刻变重。

优化：Align 必经，但默认并入现有交付清单和 PR/MR；只有 L3、高风险或审计任务独立留证。

### 问题四：模板存在规则重复

TEST-PLAN 重新抄写了 SOP 中的 TDD 规则，未来两处容易不一致。

优化：TEST-PLAN 只记录测试先行例外，统一规则留在 SOP。

### 问题五：模板元数据可能与任务系统重复

负责人、状态、评审人和更新时间通常已由任务系统维护，双写会产生偏移。

优化：README 明确允许删除已有系统负责的重复元数据，模板只提供无外部系统时的默认值。

### 问题六：设计示例容易伪装成已交付

L3 异步导出示例拥有完整 PRD、SDD 和测试方案，但没有代码和真实测试，不能判定为完成。

优化：为示例增加明确的 Align Fail 记录，证明文档完整不能替代实现证据。

### 问题七：最终 Gate 可能诱发最后补文档

若团队只在 Done 前一次性对齐，文档会在开发过程中失去作用。

优化：SOP 规定需求变化立即回 Ready、设计变化立即回 Build；最终 Align 只是安全网。最后需要大量补写本身就是流程异常信号。

## 3. 优化后的最小执行方式

- L1：任务描述 + 验证 + 一行 Align 结论。
- L2：单份 SPEC + 交付清单中的 Align。
- L3：PRD/SDD/TEST-PLAN 按需拆分；重大决策写 ADR；高风险时单独保存 Align 证据。
- 所有等级：权威冲突未解决时不能 Done。

## 4. 尚未证明的部分

- 尚未在真实多人项目和真实 PR/MR 中测量评审耗时。
- 尚未证明 Gate 能降低线上缺陷或返工率。
- 尚未接入 Jira、GitLab、GitHub 或 CI，因此当前依靠执行者和评审者检查。

下一步不应继续增加模板，而应选择真实 L1、L2、L3 任务各运行一次，记录编写时间、发现的偏移、返工和交接效果。
