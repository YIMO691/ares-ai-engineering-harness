# 工程规则：代码、验证与评审

按本次改动与实际风险选择适用内容。遵循目标项目的语言、格式、权限和发布要求；本文不规定统一测试数量、覆盖率、注释比例或固定 Agent 编排。完成判断集中在 [流程](WORKFLOW.md#交付与后续)。

按问题跳转：[验证方法](#验证覆盖与方法) · [失败诊断](#检查没有给出结论时) · [契约与分端](#设计契约与分端协作) · [结果未知](#超时重试与结果未知) · [评审](#评审与清理)。

## 可维护的代码

通过命名、类型、边界和清楚的结构表达意图，避免把多条关键语句压在一行。改动聚焦目标，不顺手重写无关模块。错误处理符合项目约定，不能吞异常或默认成功来掩盖未完成逻辑。

公共接口、数据或配置变化检查调用方、默认值、版本兼容与失败语义。生成代码、Schema、迁移和契约定义保持明确来源，手写文档引用它们，避免维护另一份机械副本。

## 注释与性能说明

注释解释原因、约束与不变量，重点包括复杂业务规则、生命周期、并发、缓存、兼容处理及必要接口副作用。显而易见的控制流不需要逐行翻译。临时兼容和 TODO 应说明移除条件或相关任务；失真注释随代码修正。

不强制每个方法都写 Big-O。非平凡算法、热点、易退化路径需要有依据的规模与复杂度说明；数据库、网络和异步流程优先说明外部调用次数、批量上限、最坏扇出、分配量和锁等待。无法证明的结论不猜测。

```text
示意：一次批量查询；内存随 pageSize 增长；不持锁执行外部 I/O。
说明成立的规模和条件，实际优化时用测量支持结论。
```

重要性能优化先定位瓶颈，再比较适用环境下的前后结果。格式问题优先使用项目已有工具；人工和 AI 评审把精力用于行为、约束与设计。

## 验证覆盖与方法

验证围绕改变的行为与主要失败后果安排，文档规模不决定验证强度：

| 变化或风险 | 应考虑的验证 |
|---|---|
| 核心规则、缺陷、数据转换 | 正常、边界、非法输入和相关回归；适合时测试先行 |
| 界面与用户操作 | 主要路径、失败反馈和必要人工/端到端检查 |
| 跨模块或 Client/Server | 契约、错误映射、旧端兼容和适用联调 |
| 状态、并发、生命周期 | 重复操作、取消、重试、资源释放、恢复与竞态 |
| 迁移或难回滚变化 | 数据兼容、迁移/回滚或替代恢复方案 |
| 权限、安全或敏感数据 | 越权、数据边界、日志泄露和项目要求的专项检查 |
| 热点或性能目标 | 代表性规模、测量条件与回归影响 |

以上是思考线索，不是每个任务必跑的完整清单。简单文档改动检查文档即可。测试用例应能区分正确与错误行为，避免只复述实现；不要为了绿色结果删除有效测试或削弱约定目标。

测试预期来自已确认规则、独立算例或可信样本，避免在断言里重写实现算法。先明确在哪个可观察接口验证；单元、契约、持久化和端到端检查各有用途，不能只因某个技能偏好最高层接口，就省略关键数据库约束或跨端兼容验证。场景表和测试计划没有实际执行结果时仍是计划。

测试命令成功不代表发现了足够测试或覆盖了所有验收项。检查实际结果与相关断言，必要时说明测试发现数、具体场景、执行环境和源码版本。已有 CI 报告可直接引用；手工验证记录操作、观察与限制。未执行与部分完成如实说明，不存在适用于所有任务的“完整测试”证明。

### 检查没有给出结论时

按实际问题记录下一步，不把所有情况都写成“测试失败”或靠重跑直到绿色：

| 现象 | 先收集什么 | 怎样继续 |
|---|---|---|
| 命令退出成功，却没有目标场景结果 | 实际发现/执行的用例、过滤条件与报告 | 确认目标场景确实运行后，才能解释其结果 |
| 环境准备或依赖访问失败 | 失败阶段、环境版本、可脱敏的诊断 | 修复前置后执行受阻场景；此前记为未能验证 |
| 断言与实际行为不符 | 前置是否成立、预期来源、实际观察与代码版本 | 区分实现缺陷、测试缺陷和需求歧义，再修复或协调；不迎合实现改断言 |
| 偶发失败，重跑又通过 | 失败时序、共享状态、重试记录与受影响范围 | 保留两种观察并定位原因；一次重跑成功不抹掉未解释的失败 |

关键异步/竞态场景说明事件顺序和故障触发条件，在获准测试环境复现。替身可控制依赖的慢响应或失败，但不能证明真实依赖；实际唯一约束、跨端兼容与用户路径按其风险选择检查位置，不能从某一层通过外推全部验收。

## 设计、契约与分端协作

产品意图保留一个权威来源：功能说明维护共同规则并关联两端实现及验证。双端功能分别解释客户端和服务端的实际处理，两端引用同一可执行契约；文档选择与例外见 [工作指南](WORKFLOW.md#维护功能说明)。文件命名沿用项目约定。

Client 关注界面状态、输入、资源与生命周期；Server 关注业务规则、持久化、事务、并发、幂等和可观测性。纯服务、脚本、数据或其他项目使用对应模块划分，不强行套两端模型。重要兼容、失败恢复和数据边界在现有设计记录中说明。

旧消费者仍在使用时，比较直接替换与“引入新形式 → 分批迁移 → 确认旧调用消失 → 移除旧形式”的代价。选择依据包括部署顺序、旧端生命周期、数据迁移和回滚能力；若不能分批保持可集成，明确最终集成验证点。源码已改完不代表全部消费者已升级，不根据技能偏好擅自取消现有兼容承诺。

### 超时、重试与结果未知

远端写入超时只说明调用方没及时取得结果；取消等待也不证明远端停止。先区分明确拒绝、确定成功和结果未知，再选择提示与恢复行为：

| 已知事实 | 处理依据 |
|---|---|
| 已取得该操作的成功或拒绝终态 | 对照约定更新显示，核对当前资源状态与权限 |
| 请求超时或连接断开，尚无终态 | 保留结果未知；如协议支持，查询同一次操作，再协调资源视图；一次读到旧值不能证明迟到写入不会发生 |
| 需要重试 | 核对操作是否幂等、去重键是否仍有效，以及超时/次数预算；不能盲重试带副作用的操作或将重试当新意图 |
| 旧响应在新操作之后返回 | 按当前意图、请求归属或版本处理，避免旧结果覆盖新选择 |

幂等、顺序或恢复能力缺失时，明确约束并补必要设计；不能将结果未知伪装成已回滚或已成功。正常路径、重复请求、迟到响应和恢复测试按实际风险选择，不要求所有项目另建操作状态平台。

## 评审与清理

评审优先查目标遗漏、错误行为、失败路径、契约变化、兼容和验证缺口，再看结构与注释。独立评审要有足够上下文与可检查对象；AI 评审也有能力边界，不能保证穷尽问题。高影响或难回滚变化按项目规则安排具备责任的独立判断，不以作者自评代替。

意见应区分“为本次交付必须解决”与“可后续改进”，并说明具体影响及依据。违反已确认目标、关键数据/权限/兼容约束或缺少必要验证时，按真实风险处理；纯教学建议、风格偏好和低影响优化不能伪装成阻断。分歧先对照事实与项目规范，仍无结论时交给 [项目已有责任安排](WORKFLOW.md#开始工作)，不以无限打磨追求完美。参考 [评审标准来源](SOURCES.md#文档实践的定向核对)。

给审阅者明确起点、终点与依据：多提交任务提供整个任务的差异，不只看最后一笔；涉及未提交改动时显式包含暂存、未暂存和新文件，或先按项目规则形成可审阅提交。只比较已提交 HEAD 的工具不会自动看到工作区内容。局部检查可以使用局部范围，但不得声称已审整个任务。

评审同时关注是否满足规格、是否符合工程规则；需要分开报告时分开写，不强制固定两个代理。具体意见包含场景、影响、位置及版本。逐项记录修正、反证不采用或仍待决定，修复后重验原问题和受影响回归；复查从上次所审版本定位修复，跨接口风险按调用关系扩展。反复无新证据时调整诊断路线，不能以达到固定轮数替代未解决的验收。

代码和规格同时改过只说明共同发生了变动；文件级漂移检查不能证明行为同步。审阅时仍核对修改的规则、保留的约束与当前验证结果。

提交前清理临时代码、调试开关、无效日志、死分支和过期注释，更新受影响的说明。交付用已有记录说明实际结果、偏移与遗留。模板中的示例措辞不能作为已执行结果。
