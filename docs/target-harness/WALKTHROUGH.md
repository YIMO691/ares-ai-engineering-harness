# 完整贯穿示例：任务收藏功能

这是[目标 Harness](../TARGET_HARNESS.md)的**虚构设计演练**，用于检查文档链是否连通。产品、参与者、版本、运行结果和决定均为示意，不是本仓库实现、真实测试、用户授权、验收或发布记录。`rev-A` 等是可读占位标识；真实任务必须替换为实际可定位版本及证据。

本例先展开所有角色，之后才讨论文件合并。各角色的正式定义见[文档契约目录](ARTIFACT_CONTRACTS.md)。

## 1. 从一句需求到事实、边界和产品规则

虚构需求：用户希望在工作台收藏常用任务，下次登录时仍能快速找到。

| 角色 / 示例 ID | 本例内容 | 后续依据 |
|---|---|---|
| C01 POLICY-001@r1 | 可修改任务工作台客户端、服务端、契约与测试；开发环境可验证；生产操作需对应发布授权；记录访问和证据保留规则 | BND-001、BASE-001、REL-001 |
| C02 SRC-001@r1 / INTAKE-001@r1 | 保留上述原始请求，来源定位为演练来源；目标是减少反复查找常用任务的操作 | CTX-001、PRD-001 |
| C03 CTX-001@r1 | 演练前提：现有任务列表按权限过滤，有稳定 taskId、已登录用户身份和关系数据库；当前没有跨设备收藏 | 方案依赖；真实任务需附源码/数据版本证据 |
| C04 Q-001 / ASM-001 / RISK-001 | 问题：收藏是否跨设备、数量上限、失权后展示？假设数据库支持事务与唯一约束。风险：并发突破上限、越权泄漏、重试重复写入 | 在设计或基线前解决相关未知 |
| C05 BND-001@r1 | 包含收藏/取消、列表与持久化；不含分享、离线同步、自定义排序；保持原任务访问权限；不自动授予生产发布权 | PRD、SPEC、审查、发布 |

演练设定产品负责人回答：收藏跨设备；初版最多 20 条；按收藏时间倒序；失去访问权限后立即不可读取任务信息，重新授权后保留原收藏；不可访问的收藏仍计入数量，客户端只显示不含任务信息的清理入口。数据库能力仍需工程验证，不能由产品回答替代。

PRD-001@r1 将该回答转成需求 `REQ-001` 和稳定 AC：

| AC | 产品可观察结果 | SPEC 的规则 |
|---|---|---|
| AC-001@r1 | 收藏可访问任务后，重新登录或换设备仍可见；取消后不再出现在收藏列表 | RULE-001 持久化与幂等变更；RULE-004 排序 |
| AC-002@r1 | 已有 20 条时，新增被拒绝；并发与重试不产生重复或突破上限 | RULE-002 原子上限与唯一性 |
| AC-003@r1 | 用户不能借收藏读到无权限任务；失权后只见可清理的匿名记录 | RULE-003 访问与展示边界 |
| AC-004@r1 | 正在处理与失败状态可识别；重试不会让界面显示与服务器相反的最终状态 | RULE-001、RULE-005 客户端状态恢复 |

产品价值指标暂定为“找到常用任务的步骤和耗时是否减少”；具体收益待实际用户评估。此时不能宣称节省了多少时间。

## 2. SPEC、设计、契约和 ADR 怎样分工

**C07 SPEC-001@r1** 精确定义以下行为：

- `RULE-001`：收藏是设置目标状态，不是 toggle。相同用户与 taskId 只有一条记录；重复设置为已收藏返回当前状态，时间顺序不因重试改变；取消不存在记录视为已取消。
- `RULE-002`：上限按用户的全部持久收藏计算，包括匿名记录。并发新增必须原子判断，不能同时读到 19 再都成功。已收藏任务的重复设置不占新名额。
- `RULE-003`：身份来自认证上下文；写入收藏需校验任务访问权；列表每次读取重新校验权限。失权记录仅返回不含 taskId/标题的 opaque favoriteId 清理句柄；取消按本人拥有的句柄执行，外部用户不能借句柄读写记录。
- `RULE-004`：按首次收藏时间倒序，同一时间按稳定 favoriteId 排序。取消后重新收藏生成新的收藏时间。
- `RULE-005`：客户端区分 idle、pending、confirmed、failed。请求超时不假定服务端未写入；重试使用相同目标状态，重读服务端后恢复展示，不以本地动画当作成功。

**C08 SDD-001@r1** 决定由服务端保存收藏关系，客户端持有显示缓存。每用户新增收藏通过数据库事务中的用户级串行化保证计数与插入一致；数据库唯一约束保证 `(userId, taskId)` 唯一。列表按实时权限过滤，并为失权记录生成匿名输出。设计还定义日志中不记录任务标题、操作失败计数、延迟观察与数据保留随账号生命周期处理。

**C09 CONTRACT-001@r1** 给出共享语义；真实项目应再落入可执行 schema/proto：

| 契约 ID | 输入 / 输出 | 约束 |
|---|---|---|
| API-001 | `PUT /me/favorites/tasks/{taskId}` → 当前收藏记录 | 设置已收藏，身份由认证提供；错误含无权限、上限达到和暂时失败 |
| API-002 | `DELETE /me/favorites/{favoriteId}` → 已取消 | 句柄必须属于当前用户；重复删除按幂等语义处理，不泄露他人记录是否存在 |
| API-003 | `GET /me/favorites` → 可访问任务条目或匿名清理条目 | 匿名条目只含 opaque favoriteId 与 unavailable 状态；返回当前上限和计数 |
| DATA-001 | 收藏表、唯一键、排序字段和必要索引 | 明确时间精度、并发锁定与迁移；旧客户端忽略未知可选字段 |
| CFG-001 | 服务端收藏上限，初值 20 | 服务端为权威；客户端读取返回的 limit，不硬编码 20 |

**C10 CLIENT-001@r1 / SERVER-001@r1** 分别展开界面状态、请求恢复、匿名记录清理，和校验顺序、事务、访问过滤、错误映射。引用上述规则和契约，不在两端文档重新发明不同的上限或重试语义。

**C11 ADR-001@r1** 记录“服务端持久化 + 目标状态操作 + 数据库约束”的取舍：满足跨设备与并发要求，代价是网络依赖和写入串行化成本；若出现高频热点用户或数据库约束不成立，重新评估。验证阶段必须检查实际数据库行为，不能只相信设计描述。

## 4. 实施、失败、修复与独立审查

以下都是**推演的分支结果**，用于展示怎样记录；没有真实执行任何测试。

1. **C16 CHANGE-001@rev-A** 对应 INC-001：第一版在应用层先 count 再 insert，仅用了唯一约束。
2. **C17 RESULT-001 / run-A**：假设 TC-002 实际观察到最终 21 条，应记录 FAIL、输入、并发方式、实际结果和证据；不能因为总体测试命令跑完就写通过。
3. Primary 确认属于 `RULE-002` 的实现缺陷，沿原 BASE-001 返工；不需要把上限改成 21 来让测试通过，也不因此重开 PRD。
4. **CHANGE-002@rev-B** 补齐每用户事务串行化。**RESULT-002 / run-B** 记录新版本的测试及回归结果；若实际通过，引用新的原始证据。旧 run-A 失败保留。
5. **C18 REVIEW-001** 假设发现 `FIND-001`：匿名记录仍返回 taskId，违反 RULE-003。记录受影响源码位置、泄漏路径、重要程度与判据。
6. **CHANGE-003@rev-C** 修复输出。**RESULT-003 / run-C** 重新检查权限及受影响回归；**REVIEW-002** 对新版本复核 FIND-001，并明确原审查其余范围的适用性。是否通过仍由真实观察决定。

独立 Reviewer 读取规则、实际源码、差异和证据。Primary 修复说明只能作为输入，不能代替复核。

| AC 修订 | 规则 / 契约 | 实现 / 测试 | 当前证据与审查 |
|---|---|---|---|
| AC-001@r1 | RULE-001、004 / API-001、002、003 | rev-C / TC-001、006 | RESULT-003 对应场景；REVIEW-002 适用范围 |
| AC-002@r1 | RULE-002 / DATA-001、CFG-001 | rev-C / TC-002、003 | 新并发/幂等结果；历史 FAIL 仍链接 |
| AC-003@r1 | RULE-003 / API-001、002、003 | rev-C / TC-004 | 权限结果；FIND-001 修复与复核 |

## 6. 发布与运行反馈

**C22 REL-001** 分为提前准备的计划与之后补充的实际执行记录：

- 计划：先做可兼容的增量表迁移，再部署服务端，最后启用客户端入口；功能开关控制展示。记录目标环境、制品版本、备份、健康判据和执行授权。
- 回滚：关闭入口并回退到兼容旧版本；暂保留新增数据，避免回滚时破坏已产生收藏。若要删除数据，需按数据策略和实际授权另行处理。
- 验证：上线后检查收藏读写、权限与错误率；达到预设异常条件时停止扩展并按预案恢复。计划中的阈值要在真实发布前确定，不能事后为成功改写。
- 执行：记录实际动作、时间、版本、观察与异常。若发布请求超时，先查询环境实际版本；不能直接重复迁移。

**C23 OPS-001** 记录发布后观察窗口、使用情况、延迟和失败、告警归属及隐私限制。假设线上发现“客户端重试导致短时重复请求”，先区分流量增加与数据重复：前者可能是优化需求，后者可能违反 RULE-001。形成事件记录和证据，再更新 Context 或提出变更。

**C26 EVAL-001** 评价用户是否更快找到常用任务，以及 Harness 的 Context 整理、并发测试和 Reviewer 是否减少缺陷、付出多少额外时间。样本不足时保留观察与后续评估计划，不宣称已经证明效率提升。将并发上限、响应丢失和匿名字段泄漏转成可复用回归场景。

## 7. 中途将上限从 20 改为 50

**C24 CR-001** 假设发生在 rev-C 交付之后：产品提出上限变为 50。原 SRC-001 和 BASE-001 保留，新来源为 SRC-002。`AC-002` 保持身份，修订为 r2；CFG-001、RULE-002、SPEC/PRD 和相关测试形成 r2，不通过修改旧文档让旧验收看似涵盖新规则。

| 对象 | 影响分析 | 后续 |
|---|---|---|
| PRD/SPEC/CFG 上限定义 | 产品规则变化 | 形成 r2，实际确认变更并建立 BASE-002 |
| SDD 事务策略 / API 形状 | 机制和字段可能不变，容量假设需要核对 | 记录保留设计的依据与新适用基线；不是自动继承 |
| CLIENT 显示 | 从服务端读取 limit，可能无需改代码 | 核对没有硬编码；验证新值显示 |
| TC-002 | 19→20 的旧场景不证明 49→50 | 升级 r2；新增 20→21 可成功、49 并发→50、50 拒绝新增 |
| TC-003 及其他测试 | 幂等、权限和排序语义未改；新配置/源码的运行适用性仍要核对 | 依据影响分析与现行检查策略确定重验范围 |
| RESULT-003 / REVIEW-002 / ALIGN-001 | 保留对旧基线的历史效力；不足以覆盖 r2 全目标 | 新结果/审查范围、ALIGN-002 和 DELIVERY-002 |
| ACCEPT-001 / REL-001 | 只描述旧交付及其真实决定 | 新版本有自己的决定和发布记录；不覆写旧记录 |

当前 CLI 没有上述完整细粒度依赖引擎；实际执行仍遵循现有源码/文档变化校验和重新提交验证要求。这个示例定义的是目标影响传播，不能据此绕过现行检查。

## 8. 中断与交接

**C25 HANDOFF-001** 假设写于 rev-B 验证中断时，至少说明：

| 信息 | 本例应记录 |
|---|---|
| 当前依据 | BASE-001 与全部有效文档修订；尚未发生 CR-001 |
| 已完成 | INC-001 初步实现及并发修复；rev-A 失败保留 |
| 正在进行 | run-B 状态未知，不能标通过 |
| 实际现场 | rev-B 及未提交差异、运行进程和测试环境；由工具核对 |
| 未完成 | 客户端联调、正式 Review、Align、验收、发布 |
| 授权与副作用 | 已有开发授权；没有生产发布；若有不确定写入需说明 |
| 下一步 | 查询 run-B/进程与源码，确认结果或停止残留后重新验证；不得直接从“准备验收”开始 |

接手者重新核对现状，不相信过时的“下一步”。这份记录帮助继续业务工作，不依赖透明恢复原来的模型会话。
