# 目标 Harness 文档契约目录

本文配合[目标总纲](../TARGET_HARNESS.md)使用，定义完整理论中的文档角色。**所有字段和标识都是目标语义，不是当前 CLI 新增字段或自动生成承诺。** 同一文件可承载多个角色，但应能定位到各自的权威内容。下面的完成条件不是逐项人工审批要求。

## 1. 统一规则与目录

每个角色都要能回答：依据什么输入、由谁维护、包含什么、什么时候有效、谁使用它。共同的身份、版本、依赖、证据和权限语义见[总纲元数据](../TARGET_HARNESS.md#62-目标元数据契约)。缺失信息显式标记待确认或未验证，不用完整格式掩盖内容缺口。

## C01 PROJECT-POLICY：项目规则与能力约束

**输入**：已有项目规则、用户授权、工程环境和适用的组织要求。**维护者**：项目维护者；Primary 汇总并核实。

内容包括规则来源与优先级、允许读写的范围、工具和环境入口、构建/测试方式、分支与发布约定、数据分级和证据保留、必要审查策略、权限与升级条件。记录适用项目及版本；区分“工具具备能力”和“本任务获准使用”。专门领域要求应明确来源和复核角色，不自行宣称合规。

领域 profile 和检查规则需带适用版本、执行方式、成熟度、维护者与例外；半机械风险信号不直接作为硬门禁。新规则的升级、降级与退役依据见[质量治理](../TARGET_HARNESS.md#93-确定性检查风险信号与语义判断)。

**完成条件**：足以决定本次可执行动作及所需条件；冲突可定位。**消费者**：全部阶段，尤其 BOUNDARY、BASELINE、执行和发布。用户已有明确授权应被保留，不因文档分层重复审批。

## C02 INTAKE/SOURCE：需求入口与原始来源

**输入**：需求消息、策划资料、工单、用户反馈、事故或运行指标。**维护者**：Primary；需求方对原始意图负责。

INTAKE 写问题陈述、预期价值、需求主体、优先级、时间约束、影响对象和成功信号。SOURCE 记录原始表述及可定位来源、作者/提供者、观察时间/版本、引用范围和访问限制。多来源冲突单列；后续解释链接 PRD 或决定，不覆盖原记录。

**完成条件**：能区分原始请求与工程解读；能找到来源或清楚知道无法访问。**消费者**：Context、边界、PRD、变更和最终追溯。

## C03 CONTEXT：当前事实与上下文地图

**输入**：SOURCE、项目规则、当前代码/文档/配置/数据、已有决定与运行证据。**维护者**：Primary；事实依赖实际读取或工具结果。

内容包括系统与模块地图、现有用户流程、接口和数据流、依赖版本、相关文件定位、当前行为与限制、历史决定、已知缺陷、环境与验证能力。每项关键观察关联来源版本；明确事实、推断、假设、未知，记录检查范围及未读取部分。规模较大时先有索引，再按任务逐步展开。

候选模式区分相似实现、经核验的 Golden Pattern 和反例；记录为何适用、不可照抄部分、源码版本、验证依据与失效条件。项目当前事实、确认的期望行为和共享知识分别标明，不把研究假设写成项目事实。

**完成条件**：关键方案不依赖未标明的猜测；来源可复核；陈旧事实有更新规则。**消费者**：所有设计和 Context 包。完整上下文地图不等于全部内容一次进入模型提示词。

## C04 QUESTION/ASSUMPTION/RISK：未知与风险

**输入**：来源冲突、调查缺口、设计不确定性与风险分析。**维护者**：Primary；指定解决问题的人或工具。

问题记录 ID、原问题、影响、所阻塞决定、需要的回答者和解决依据。假设记录假设内容、成立条件、验证方法和失效影响。风险记录原因、可能后果、重要程度及理由、应对方式、验证/监测和责任归属。有时限的项记录截止或触发条件。

先分流为工程调查、授权内局部可逆选择、未来非目标或需实际决策的关键未知；说明所阻塞的决定。可由工程事实回答的问题不重复交给 Owner，未知也不能为满足形式检查而被删除。

**完成条件**：关键未知在依赖它的承诺发生前解决；可延后的未知有可接受影响和后续动作。探索性试验需写目标、限制、结果和是否进入正式设计。**消费者**：Boundary、PRD/SPEC、设计、测试、发布和运行。不能把暂时假设无声提升为已确认规则。

## C05 BOUNDARY：范围与边界

**输入**：产品意图、Context、项目权限和风险项。**维护者**：Primary；Owner 决定业务范围与授权。

同时表达三种边界：

- 产品边界：目标、in-scope、out-of-scope、非目标、涉及用户/场景、明确保留行为。
- 工程边界：模块、端、数据、协议、外部依赖、兼容性、非功能和环境约束。
- 动作边界：允许读取/修改/执行/提交/合并/发布的对象及已有授权来源，需升级的条件。

**完成条件**：可判断一项具体变更是否在约定内；实现授权不被扩大为任意部署权限。**消费者**：PRD、SPEC、设计、基线、审查和变更分析。

## C06 PRD：产品需求

**输入**：SOURCE、Context、Boundary 与澄清决定。**维护者**：Primary 整理；Owner/产品负责人确认业务意图。

内容包括问题和价值、目标用户、核心场景与旅程、业务规则、范围与优先级、产品非功能目标、依赖、开放问题及可观察验收条件。给需求和 AC 稳定 ID，并追溯来源；说明成功衡量方式。交互流程、原型和文案在有助于判定预期体验时关联进来。

**完成条件**：读者能知道为什么做、谁使用、哪些行为算满足；关键产品冲突已解决。**消费者**：SPEC、设计、测试、验收和运行效果评估。PRD 不提前用实现细节替代用户问题。

## C07 SPEC：行为规格

**输入**：PRD/AC、Boundary、已核实 Context。**维护者**：Primary；业务歧义回到 Owner。

内容包括术语、输入/输出、前置与后置条件、状态机、规则 ID、不变量、正常/异常/边界路径、时间语义、幂等/重复/并发、权限、错误和兼容行为。非功能要求变成可判定条件，并标记验证环境。每项规则引用需求/AC；示例辅助消歧，不能替代一般规则。

内容按当前行为与风险选取，保留足够精确的关键语义；以不变量和可执行判据补充代表性场景，不要求人类穷举所有未来情况。

**完成条件**：独立读者能够为主要行为写出测试判据，未决定的行为不会被实现者随意补全。**消费者**：SDD、CONTRACTS、详细设计、TEST-PLAN、Reviewer 和对齐。

PRD 与 SPEC 分别回答“产品要什么”和“准确行为是什么”；SDD 回答“如何实现”。当前 L2 文件名也叫 SPEC，不表示它与此处独立行为规格的语义完全相同；当前 L3 尚无独立 SPEC 文件。

## C08 SDD：总体技术设计

**输入**：SPEC、Context、Boundary、风险和能力限制。**维护者**：Primary；重大取舍写 ADR。

内容包括模块职责、组件关系、调用与数据流、存储和数据生命周期、事务/一致性、失败恢复、权限与信任边界、性能/容量策略、可观测性、外部依赖、迁移与兼容、部署与回滚思路。标明规则/AC 的实现归属、替代方案和残留风险，链接后续契约与详细设计。

新增抽象、依赖、跨模块状态或扩大变更面时说明当前必要性和简单替代方案。按需关联本轮质量关注点、状态 owner、项目模式、领域约束与验证方式；不要求单独生成 QUALITY-CONTRACT 文件。

**完成条件**：跨模块责任和关键机制不留空；方案能满足规格或明确暴露不可满足项。**消费者**：CONTRACTS、端设计、计划、测试和运维准备。

## C09 CONTRACTS：接口、数据与配置契约

**输入**：SPEC、SDD、生产者/消费者需求。**维护者**：契约责任方；Primary 保持两端一致。

内容包括 API/消息/事件、请求响应、schema/proto、字段单位/范围/缺省/可空性、错误语义、身份与授权、幂等键/排序/超时/重试、兼容策略和版本协商。数据/配置契约还包括约束、索引、来源、加载/更新、迁移、保留和删除。说明权威定义位置、使用者、示例、契约测试与发布依赖。

**完成条件**：各实现者可独立开发并对接；代码生成输入与说明指向同一版本；旧数据/旧客户端处置明确。**消费者**：详细设计、实现、测试、集成和发布。可执行 schema 是契约载体之一，不能表达的业务约束仍要清楚记录。

## C10 DETAIL：客户端、服务端与其他详细设计

**输入**：SPEC、SDD、CONTRACTS。**维护者**：对应实现方，当前可由同一 Primary 完成。

| 侧重 | 应说明的内容 |
|---|---|
| 客户端/交互 | 数据结构、界面状态、输入/显示、请求生命周期、断线/重试、错误提示、缓存/同步、资源与生命周期、可访问性、涉及文件 |
| 服务端 | 配置适配、规则校验、候选/查询构建、业务服务、事务与并发、响应映射、存储/协议、可观测性、涉及文件 |
| 其他组件 | 任务调度、工具/库/数据管道/基础设施的输入输出、边界、状态和失败处理 |

每项关键实现引用规则与契约，说明测试切入点。**完成条件**：边界内的实现责任明确，跨端约定一致；细节允许模型在约定内自主调整并同步文档。**消费者**：实施、测试、Review、维护者。单端任务按其真实组件映射，不虚构另一端。

## C11 ADR：关键设计决定

**输入**：需要稳定保留理由的重大取舍。**维护者**：提出者记录，实际决策者确认涉及其权限的决定。

内容包括背景、约束、备选方案、选定方案与理由、正负后果、影响条目、决定主体和时间、适用版本、重新考虑的触发条件及替代关系。

**完成条件**：后续维护者能解释为何这样设计及何时需要改变。**消费者**：设计、实现、审查和未来变更。普通变量命名不必升级为 ADR；理论保留该角色，而非强制每个任务编造重大决定。

## C12 PLAN/TASKS：可验证的执行计划

**输入**：有效 SPEC、设计、风险、环境与验证能力。**维护者**：Primary。

内容包括可验证增量 ID、所覆盖需求/规则、依赖关系、顺序或可并行部分、涉及范围、完成判据、自检方式、环境/数据准备和交付节点。高不确定内容先安排调查或试验；需发布时把迁移、运维和恢复准备纳入计划。

**完成条件**：每个增量有可观察结果而非“开发完成”一句话；整体覆盖约定目标。**消费者**：BASELINE、执行、状态、交接。计划是可调整的工程方法，普通实施重排无需重新批准全部需求。

## C13 TEST-PLAN：验证策略与场景

**输入**：PRD/AC、SPEC、设计、契约和风险。**维护者**：Primary，必要时由领域验证者补充。

内容包括 AC/规则 → 测试 ID 的映射、测试层次和方法、输入/前置条件、动作与预期、环境/数据/依赖、正常/异常/边界/并发/兼容场景、非功能阈值、回归范围、人工检查、执行顺序和证据保存方式。明确不适用、暂不能验证及替代方法，记录它们支持结论的限度。

区分确定性检查、半机械风险信号、运行证据和语义判断；注明工具入口是否实际核验。必要时使用属性/不变量、负例、故障注入验证，而不是以测试数量或自评分证明覆盖。

**完成条件**：主要 AC 有能证伪实现的判据；环境与数据可准备；不存在只有测试名称没有预期的覆盖声明。**消费者**：实施、自检、正式验证、审查和验收。测试代码是此计划的可执行载体之一。

游戏体验研究在本角色中说明目标玩家、待回答问题、体验假设、观察/访谈/问卷/遥测方法、版本、替代解释和决策依据。AI 试玩的状态覆盖与真人体验有效性分别验证；按实际风险选择方法，不要求每个功能完整研究。详见[游戏体验与恢复](../TARGET_HARNESS.md#94-游戏意图体验证据与恢复)。

## C14 BASELINE：约定基线

**输入**：有效的意图、边界、设计关键决定、验证计划、项目策略、源码状态与真实授权。**维护者**：Primary 提交，Harness 管理身份与历史。

内容包括基线 ID、目标/AC/非目标、允许写入范围、关键决定、验证安排、所有参与文档精确修订、项目/源码版本、未决项处置和授权主体/来源/范围。引用长期文档，保存足够的本轮执行语义，避免只有不可访问的链接。

本轮采用的质量约定、模式与规则版本应可定位，实质变化需评估是否使既有基线失效；原始研究的状态标签不授予实施权限。

**完成条件**：可以明确说出按什么约定实施；阻断性未知已解决；实际授权存在。**消费者**：执行、验证、Review、Align、交接。修改长期文档不静默改写冻结基线。

## C15 CONTEXT-PACK：模型工作包

**输入**：基线、当前阶段/增量、相关事实、差异、历史反馈和可用工具。**维护者**：Primary 选择语义，目标 Harness 支持定位和版本记录。

内容包括当前目标与下一步、关键规则和约束、相关源码/文档位置与版本、事实/假设/未知、失败与审查反馈、环境能力、包含/省略/截断的范围、重新读取条件和停止/升级条件。摘要应带来源，关键约束不得仅因篇幅预算被无声删除。

只加载当前目标相关的模式与反例，包含适用/不适用场景和不能复制的业务特例；留出继续按需查证的入口。上下文包描述事实与约束，不预先指定无依据的实现结构。

**完成条件**：接收模型知道任务、边界、判据及如何补充读取，能识别不足。**消费者**：当前 Primary、独立 Reviewer 或实际获准的交接执行者。工作包不替代原生会话管理，不要求导出完整对话或隐藏推理。

## C16 CHANGESET：实现与增量记录

**输入**：基线、增量计划与工作包。**维护者**：实际实施者；工具提供差异和版本事实。

内容包括已完成增量、实际改动文件/对象、代码或内容版本、规则/AC 引用、必要设计变动、测试/自检、失败和残余问题、外部副作用及范围核对。构建产物和依赖清单在涉及交付制品时关联。

**完成条件**：能从记录定位实际改动，并知道哪些仍未验证；设计变动已同步或转为变更请求。**消费者**：验证、Review、Align 和 Delivery。变更说明不是实现证据本身，必须关联可检查差异。

## C17 TEST-RESULT/EVIDENCE：验证结果与证据

**输入**：TEST-PLAN、具体改动版本、实际环境与工具执行。**维护者**：工具或实际执行者生成事实，Primary 汇总。

每次运行记录 Run ID、测试/场景 ID、所依据规格修订、源码/制品版本、测试实现版本、环境/配置/数据、执行时间、执行者/工具、实际命令或步骤、预期与观察、结果、原始证据定位和完整性信息。结果区分失败、阻塞、未运行、不适用和无法定论；记录跳过原因、缺陷和复验关系。

**完成条件**：结论有足够证据且适用于所声明版本；必要检查未通过时可生成有效的失败报告，但不能进入“验证通过”。**消费者**：修复、Review、Align、验收和运行评价。成功的 build/test 方法级产物不能自动证明其中每个业务场景已通过。

体验证据另明确观察到的行为、玩家自述、研究者推断及适用群体，区分发生事实与原因解释。自动探索找到异常不等于体验已验证。缺失/相互矛盾的证据保留，重新设计或更新意图需要真实决定，不能把偏离预期一律归为实现缺陷。

## C18 REVIEW：审查与问题处置

**输入**：约定规格、当前差异、相关源码、测试和上下文。**维护者**：独立只读 Reviewer 记录发现；Primary 处理；必要决定由相应负责人作出。

内容包括审查者/上下文身份、所审版本、范围与未覆盖部分、需求/设计/实现/测试一致性、发现 ID、重要程度、具体位置、证据、影响、建议及结论。发现关联修复版本、复验或复审、实际风险接受决定或有依据的撤销。

正确性发现与可维护性发现分别说明证据和影响；按本轮约定检查必要复杂度、局部性、可理解性、验证能力和项目适配，不使用可抵消硬性失败的综合质量分，也不以审查为由扩大重构范围。

**完成条件**：阻断问题得到有效处置；审查限制明确；结论适用于最新相关版本。**消费者**：返工、Align、交付与质量评估。无发现不等于已证明所有路径正确；改动后旧审查不得自动覆盖新代码。

## C19 ALIGNMENT：全链对齐

**输入**：当前基线、PRD/SPEC、设计/契约、改动、验证和 Review。**维护者**：Primary 汇总，Harness 校验可机械判定的部分。

内容包括稳定 AC → 规则 → 设计/契约 → 实现 → 测试 → 当前结果的矩阵；文档、实现与约定的偏移；Reviewer 发现处置；清理/迁移状态；未覆盖与残余风险；每项证据支持范围及新鲜度。记录偏移是修实现、更新非语义说明还是重新确认约定。

**完成条件**：不存在未解释的关键不一致；全部验收项有适用证据或真实决定允许的明确后续；不得用“已对齐”掩盖未验证。**消费者**：Delivery 和实际验收。部分交付需要明确范围，不能给整个原目标盖章。

## C20 DELIVERY：最终交付包

**输入**：有效 Alignment、交付版本、项目文档、制品与限制。**维护者**：Primary。

内容包括交付摘要、目标与实现结果、交付版本/变更范围、功能/规格/设计/接口入口、构建制品与获取方式、安装/使用/集成说明、AC 证据索引、审查与缺陷状态、兼容/迁移/回滚、已知限制、未完成项负责人，以及验收和发布状态。

**完成条件**：接收者可访问并使用交付物，可定位判定依据；索引不引用本机私有路径充当公开证据。**消费者**：Owner、接手维护者、发布执行者。测试/审查结果可先交付，尚无实际决定时标“待验收”，不能补造 ACCEPTANCE。

## C21 ACCEPTANCE：验收决定

**输入**：明确交付版本、AC/对齐、约定人工检查与验收者实际反馈。**维护者**：实际验收者决定，Primary/Harness 如实记录。

内容包括验收人和权限、时间、来源、所验版本和范围、实际检查结果、接受/拒绝/部分接受/待定、原因、接受的限制、剩余动作和责任。合并授权、业务验收和生产发布授权各自明确，不互相暗示。

**完成条件**：已有真实决定且适用范围无歧义；没有决定则保持待验收。**消费者**：任务完成判断、交付索引、发布和历史。修订后的交付需要重新判断旧决定是否适用，不能更换版本后复用旧签字。

## C22 RELEASE：发布计划与执行记录

**输入**：目标环境、交付基线、发布准备、实际授权及适用验收状态。**维护者**：获授权的发布者；Primary 可维护计划。

发布计划提前记录制品/配置版本、环境差异、依赖顺序、数据迁移、备份、灰度/开关、健康判据、停止与回滚条件、恢复步骤、数据兼容限制和责任人。执行记录补充真实时间、动作、工具结果、发布后版本、健康检查、异常和恢复结果。

**完成条件**：实际执行可验证，健康判据已有观察；失败、部分部署或回滚如实记录。无发布行为标不适用及理由。**消费者**：Operations、Delivery 索引、事件处理与评价。准备好了回滚方案不等于回滚已演练，合并代码不等于已部署。

## C23 OPERATIONS：运行观察与事件

**输入**：发布版本、可观测性设计、运行手册和实际指标/用户反馈。**维护者**：运行负责人；工具记录数据。

内容包括环境/时间窗口/版本、健康与业务指标、阈值及告警归属、日志/追踪定位、容量/成本观察、事件影响、时间线、缓解/回滚与恢复证据、后续原因调查和责任。手册记录值守入口、常见故障处理、备份恢复与数据保留。

**完成条件**：观察范围和限制清楚，事件有处置与后续归属；“暂未收到投诉”不能替代健康验证。**消费者**：新需求、Context、风险、回归测试和 Evaluation。

游戏遥测记录事件语义、版本、来源、重复/缺失处理和玩家分组，行为变化同时保留可能原因与定性验证。奖励、货币、存档等记录实际副作用和补偿/恢复验证；代码回滚、聊天回滚不代表业务状态已恢复。

## C24 CHANGE-REQUEST：需求与约定变更

**输入**：新需求、新事实、审查/运行反馈或拟改变的约定。**维护者**：Primary 分析，涉及意图/授权的决定交相应负责人。

内容包括变更 ID、触发者/来源、旧规则/基线、新意图、原因、影响的产物 ID/修订、兼容/成本/进度/风险、选项、实际决定和新基线。逐项记录下游是失效、保留并说明依据，还是待核对；关联重新设计/实施/测试/审查/验收。

**完成条件**：变更不混入旧约定，受影响结论没有被无依据继承。**消费者**：全链相关产物。范围内的修复可以只走缺陷/返工记录；无需一律形成新产品需求。

## C25 STATUS/HANDOFF：进度、中断与交接

**输入**：真实执行状态、基线、工作区、Run、阻塞与待办。**维护者**：当前执行者，恢复者核对现场。

内容包括任务/基线身份、已完成/进行中/未开始增量、当前代码差异与文档修订、有效和失效证据、失败原因、待确认问题、已有授权、正在运行或状态未知的外部动作、下一步和恢复检查。交接说明接收者需要读取什么，不复制全部历史。

**完成条件**：另一个获授权执行者无需猜测已发生的事实即可继续；未知副作用明确标出。**消费者**：当前 Primary 或实际接手者。继续前检查现场；不能把计划操作写成已完成操作。

## C26 EVALUATION：效果评估与改进

**输入**：交付、运行反馈、可观察过程记录、模型/工具/策略版本与成本。**维护者**：Harness/项目维护者。

内容包括评估问题、任务集及来源权限、基线与候选配置、预先约定指标、质量/时长/成本/人工介入、失败分类、有效审查发现、上下文遗漏与恢复表现、样本限制、结论和改进建议。将可复现失败整理为回归场景，记录更新、停用和版本。

任务先经可恢复基线、可信 oracle、隐藏解隔离与环境核验；实验固定主要条件、重复 trial，并区分坏题、环境、工具和实现失败。质量对照与需求治理对照分别登记变量，计入人的澄清/复核和全部工具成本；模式/规则晋升或删除都需可追溯依据。

**完成条件**：结论有真实样本依据，相关性与因果假设分开；未完成实验明确未评估。**消费者**：模型/工具/Context/流程改进和下一轮需求。没有真实数据时只能提出评估计划，不能宣称 Harness 已提升效率。

当前可选的[ANGE Eval](../../tools/ange-eval/README.md)实现本角色中的协议/运行记录结构检查与描述性汇总，格式见工具文档；它不是 Direct CLI 新请求字段。记录计划运行、冻结配置、指标的数值/缺失原因及证据引用，保留失败与协议偏离。完整记录、工具退出码 0 和中位数差异不证明方法有效；真实效应分析、玩家研究和证据真实性仍需独立评价。

## 2. 交付前的角色覆盖核对

理论评审应逐项确认 C01–C26 都有定义；项目实例则为每项指向实际载体、外部系统或有理由的不适用。再沿一个稳定 AC 检查来源、规格、实现和证据，沿一次变化检查失效传播，沿一次中断检查交接恢复。

完整角色实例见[贯穿示例](WALKTHROUGH.md)。实际载体选择遵循[落地裁剪规则](../TARGET_HARNESS.md#12-落地裁剪规则)，不以缺文件直接判定缺职责，也不以文件存在直接判定职责已经完成。
